# ValidateAgent - 旅行方案审核 Agent

审核 PlanAgent 方案的预算、交通、偏好、天气、时间、完整性与来源，并提供定位明确的修改建议。
网站和独立入口均先执行规则检查，再由模型补充语义判断；规则发现的严重冲突不能被模型覆盖。
本文统一记录使用方式、审核协议、规则、自动修复、页面验收与评估。

## 安装

```bash
cd ValidateAgent
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

在 `.env` 中填写 OpenAI 兼容接口的 Key、地址和模型；不要提交真实密钥。

## 使用入口

下面两个命令在 `ValidateAgent` 目录执行：

```bash
# 单独审核：输入 plan/profile/preferences/recent_trips/search/basic
cat validate_input.json | .venv/bin/python validate.py

# 独立规划与审核循环：输入 PlanAgent 的完整规划上下文
cat loop_input.json | .venv/bin/python run.py
```

`basic` 保存用户明确需求，`search` 保存来源信息。独立循环需要先配置 `PlanAgent/.venv`，
会携带规划时补搜的餐厅与酒店来源，返回 `passed/plan/audit/history/final_feedback`。
默认首次生成加至多一次修正；显式 modify 只修改并审核一次，避免重复执行用户指令。
服务错误或无可修复严重问题时保留方案；最后未通过时返回真实结论。
网站通过 Orchestrator 实时审核，至多自动修复两次（三次审核），与独立 CLI 的轮数限制不同。
普通建议、暂无报价及服务错误不会触发自动重新规划。

在仓库根目录可只执行规则，不需要模型 Key、网络或第三方 Python 库：

```bash
python3 ValidateAgent/rules.py < ValidateAgent/examples/rules_input.json
```

示例为合成数据。输入为 `{"plan": {...}, "search": {...}, "basic": {...}}`；
也可保存实际方案、完整搜索快照和明确需求，使用同一入口检查。
审核协议、规则及网站流程见下文。

## 离线测试与评估

测试文件统一位于 `ValidateAgent/tests/`。在仓库根目录执行，不调用真实模型：

```bash
ValidateAgent/.venv/bin/python -m unittest discover -s ValidateAgent/tests -t . -p 'test_*.py' -v
Orchestrator/.venv/bin/python -m unittest discover -s Orchestrator -p 'test_audit*.py' -v
```

也可按模块运行，例如：

```bash
ValidateAgent/.venv/bin/python -m unittest ValidateAgent.tests.test_rules -v
```

固定评估只使用标准库和合成案例，不调用模型或网络：

```bash
python3 -S ValidateAgent/evaluate.py
python3 -S ValidateAgent/evaluate.py --check
```

[评估报告](evaluation/report.md)展示预期状态、严重问题定位、误报与漏报、证据值匹配和来源覆盖。
案例与完整问题报告分别位于 `evaluation/cases.json` 和 `evaluation/report.json`。
`hybrid_fixture` 为预置模型输出；其结果不能用于声称真实模型准确率。
前端自动验证命令和完整网站手动验收步骤见下文。

## 范围

统一审核输出、错误状态、问题定位与独立/主流程的上下文传递。实现位于 `shared/audit.py`，
由 ValidateAgent 和 Orchestrator 共同调用；没有模型 SDK 或第三方依赖。

第二阶段新增 `ValidateAgent/rules.py` 的独立规则检查；第三阶段已接入网站与独立循环，
先规则检查，再由模型补充语义判断。第四阶段已接入修改后的再次审核和版本失效；第五阶段已接入问题定位与固定案例评估；网站还提供实时自动审核与修复浮窗。

## 输入

`validate_plan` 的参数为 `plan`、`profile`、`preferences`、`recent_trips`、`search`、`basic`。
调用方使用关键字参数，避免函数增加参数时产生错位。

- `plan`：实际方案、活动、路线、按方案费用、未知报价、可选 revision。
- `basic`：用户明确需求与硬约束；可选 `hard_limits` 为明确的数值专项上限（不是自动生成的分摊预算）。
- `search`：检索来源与天气证据。
- `profile/preferences/recent_trips`：画像、长期偏好和历史行程；不能替代用户明确要求。

## 输出示例

```json
{
  "schema_version": 1,
  "status": "blocked",
  "passed": false,
  "plan_revision": 3,
  "reviewed_styles": ["经典路线", "探索路线"],
  "checks": {"rules": "completed", "model": "completed"},
  "issues": [{
    "severity": "high",
    "type": "时间",
    "detail": "活动结束后无法按现有交通耗时赶上列车。",
    "suggestion": "提前结束活动，保留进站时间。",
    "actionable": true,
    "source": "model",
    "plan_style": "经典路线",
    "day": 2,
    "date": "2026-10-11",
    "block_ids": ["b-activity", "b-train"],
    "evidence": [{"path": "plan.legs[2].duration_s", "value": 2700}]
  }],
  "feedback": "请调整活动结束时间。"
}
```

示例仅说明结构，实际定位字段必须对应输入中的真实活动与路线。
`passed/issues/feedback` 继续兼容原前端；新增字段由服务端生成或校验。

| status | 含义 | passed |
| --- | --- | --- |
| passed | 审核通过，没有问题 | true |
| warning | 审核通过，保留风险或优化建议 | true |
| blocked | 审核未通过 | false |
| error | 审核没有完成，包括初始化、超时或输出无效 | false |

`error` 状态包含安全的 `error` 文本和 `feedback`；不能视为发现了行程硬冲突。
`plan_revision` 来自待审方案；老方案没有合法非负整数 revision 时返回 null。
`reviewed_styles` 来自方案数据，不由模型声明。

## 问题字段

- `severity`：high、medium、low。high 表示有证据的执行冲突或违反用户明确硬约束。
- `type`：预算、交通、偏好、天气、时间、完整性、真实性。
- `detail/suggestion`：非空文本。
- `actionable`：明确的布尔值；缺失时默认 false，避免未经确认的自动修复。
- `source`：model 或 rule，由调用审核协议的可信代码指定，忽略模型自行填写的来源。
- `plan_style/day/date/block_ids`：问题位置；跨活动冲突允许多个 ID。不能确定时使用 null 和空列表，不能编造。
- `evidence`：包含 path、value 的列表。path 为输入字段路径，value 为对应值。

校验会拒绝无效严重程度、错误字段类型、不存在的活动 ID，以及方案/日期/天数与活动不匹配的定位。
老模型输出可不带 type、定位或证据；type 默认完整性，其余为空，不会根据描述猜测活动。
通用协议校验结构；规则引擎按 path 从原始输入重新读取 value。第三阶段还会核对模型证据：
path 必须实际存在，value 必须同时对应原始输入及模型收到的字段，不把 true 当作金额1。
不使用 eval，也不通过描述猜测字段。无法核对的模型证据移除；无证据或证据不一致的模型 high 降为 medium 待核实，且不自动修复。
来源核对只表示地点出现在提供的数据中，不能证明搜索数据正确、网页仍有效或实际可预订。

模型返回 `passed=true` 却同时包含 high 问题时视为矛盾输出，再尝试一次；仍无效则返回 error。
第三阶段统一最终判定：规则问题与经校验的模型问题合并后，有 high 才阻断，只有 medium/low 则为 warning。
模型若返回 false 却完全不提供问题，视为没有有效结论，重试一次后仍无效则 error。
模型预算 high 还必须引用 `basic.hard_limits` 中有效的正数专项上限；全局总预算由规则负责核算。
只引用系统餐费分摊、历史偏好或缺失天气信息，不足以构成对应类别的模型严重问题。

## 反馈与历史

主流程和独立循环都只向 PlanAgent 发送 `high + actionable=true` 且有明确问题与建议的项。
服务错误和非严重优化不会触发重新规划。网站最多自动修复两次（三次审核）；独立 CLI 循环仍默认生成两轮。
历史保留 iteration、状态、方案版本、问题定位、证据、feedback、checks、rule_summary 和错误信息（若有），便于检查每轮结果。

## 测试边界

离线测试覆盖协议校验、旧输出适配、定位一致性、错误状态、上下文参数传递和反馈次数。
它们验证程序行为，不代表真实模型审核质量、景点来源真实性或实时行程可执行性已经通过验收。

## 第二阶段：独立规则检查

```bash
python3 ValidateAgent/rules.py < ValidateAgent/examples/rules_input.json
```

也可导入 `validate_rules(plan, search=None, basic=None)`。仅使用标准库，不调用模型、
检索工具、地图接口、网络或数据库，不修改输入，也不会自动改行程。
输入 JSON 必须为合法的对象；无效字段结构、重复 ID 和非有限数字返回结构化 error。
空活动方案返回完整性 high，不能因为没有待检查内容就算通过。

### 预算

- 只使用 `basic.total_budget`（不存在时可用数字金额的 `basic.budget`）作为硬总预算。
- 按 `plan_style` 分别核算，备选方案互不相加；`block.price` 已含人数，不重复乘人数。
- 全部报价已知时按活动价格重算；与 `cost_by_style` 不一致时提示刷新汇总，避免陈旧总价误报。
- 部分报价未知时，已知活动金额与 `cost_by_style` 所声明的已知小计取较大值，不能相加。
- 已知小计超过硬预算为 high；价格未知、金额无法解析或报价标记冲突为 medium/unknown。
- `price_known=false`、`price_source=unknown` 或显式 `unit_price=null` 均不能把 price=0 当免费。
- 明确免费及已知零价可计为0。档位、meal_budget、over_meal_budget 和系统餐费分摊不是硬总预算。

### 时间与交通

- 同一方案中按实际日期检查所有有效活动区间，包含长活动与多个短活动的重叠。
- 天气不占活动时间，酒店住宿不当成全天游览；不同备选方案互不检查重叠。
- 优先使用交通的 `dep_time/arr_time` 或 `departure_time/arrival_time` 完整时间戳。
- 支持跨日交通及明确时区；仅交通允许 `23:00-01:00` 表示次日到达。
- 没有完整日期时用 day/start_date 确定相对日期；定位字段仍只报告输入实际给出的日期。
- 普通活动倒置或零长区间为 high；日期或时间无法核实为 medium，不假设持续时间。
- `legs[].from/to` 对应活动 ID，`duration_s` 必须为有效正数。检查实际交通时间能否放入活动间隔。
- 沿用当前 PlanAgent 的进出站策略：航班120分钟、列车60分钟。它是项目策略，不是所有机场/车站的客观规定。
- 无实际路线只能提示待核实；明确不足的进出站间隔仍可依据上述项目策略阻断。
- 路线方案/日期不一致时不用于认定硬冲突；相邻地点缺少路线时提示补充。
- 这一阶段不检查营业时间、实时余票、路线实时路况或机场特殊要求，也不新增地图调用。

### 来源与链接

- 景点对应 poi，酒店对应 hotels，餐厅对应 food，活动对应 events/poi/promotions。
- 优先匹配 poi_id；名称仅统一空白、大小写和全半角格式，保留所有分店/分馆信息。
- ID 与名称明确矛盾为 high；没有 ID 且多个同名 ID 为 medium，不能随便选第一家。
- 来源明确提供的 aliases 可以匹配，不使用模型、模糊相似度或名称前缀猜测地点。
- 完整同类候选非空但无法找到地点为 high：意味着未由这些来源支持，不意味着现实中不存在。
- 来源缺失/空列表时为 medium；裁剪后的搜索输入应标记 `grounding_scope=selected`，未命中仅提示待核实。
- selected_option 支持实际名称和旧的数字索引，0 也代表已选中；尚未选定的餐厅候选组不纳入已选地点计数；自由活动、休息、候车等通用安排不作为命名地点核对。
- 地点链接缺失、无效或不能对应来源为 medium；可识别来源 poi_id 对应的高德 place 链接。
- 不打开链接、不修复链接，也不证明网页可访问。搜索描述里的指令仅作为数据，不执行。

### 数据与指标

有 blocks 时以 blocks 为准，不再次统计嵌套 schedule；没有 blocks 时支持嵌套日程，
包括单独的 day.hotel 字段。保留原始证据路径，不凭空生成活动 ID。

输出沿用第一阶段审核协议，所有问题 `source=rule`，并增加 `rule_summary`：

- `budget_by_style`：已知金额、预算状态、报价未知活动块数量。
- `grounding`：named_count、matched_count、unavailable_count、ambiguous_count、coverage。

coverage = 匹配条目数 / 命名条目数（按活动出现次数计）；没有命名条目时为 null。
缺失或模糊来源不会计入已匹配。它只度量当前输入的数据覆盖率，不代表整体真实世界准确率。
规则无 high 时可通过并保留 medium；仅规则通过不代表模型审核已完成。

### 验证

新增规则测试使用固定输入，覆盖未知报价、备选方案、人数、时间边界、跨日班次、路线耗时、
分店和 ID、链接、嵌套酒店、证据可复查以及非标准输入。
测试通过不能代替真实搜索快照和端到端验收。第三阶段新增真实规则与模拟模型的组合测试，验证来源保留、合并判定和错误路径；网站后续扩展为最多两次自动修复。

## 第三阶段：规则与模型整合

主入口 `validate_plan` 的顺序：

1. 完整的 plan/search/basic 先进入规则引擎。无效输入直接 error。
2. 规则包含 high 时，返回 blocked；模型跳过，网站按反馈机制至多自动修正两次。
3. 规则无 high 时，模型收到规则提示与指标，补充偏好、忌口、天气、营业信息等语义判断。
4. 校验模型协议、真实定位与证据后合并问题。模型通过不能删除规则风险或降低规则严重程度。
5. 有 high 为 blocked；仅 medium/low 为 warning；没有问题为 passed。模型错误为 error，保留已完成的规则问题和指标。

`checks.rules` 为 completed/error；`checks.model` 为 completed/skipped/error。
纯规则通过而模型未执行时，完整审核不能标为 passed。

`shared/audit.py` 的 `combine_audits` 合并可信规则、模型适配器输出，完全相同的判断去重并优先保留 rule 来源。
只有主流程和独立循环读取可信审核输出时使用 `normalize_audit(source="mixed")`，保留两种来源、错误时的规则问题和指标；
模型适配器仍强制使用 model，忽略模型伪造的 source/checks/revision/summary。

规则检查前不裁剪搜索候选，不移除尚未选定的餐厅 options。
模型输入仅移除重复的方案来源数据、地图 polyline 与无关搜索长文；候选顺序、别名和班次列表保留，
避免裁剪改变证据索引或漏掉实际选中的候选。
PlanAgent 返回 `source_updates.hotels` 中实际补搜的酒店，编排和独立循环将其加入完整搜索快照；
不能把方案里的地点名称本身当成独立来源。补搜报价也参与规划费用核算。

模型证据字段对应输入，只能证明其引用的数据存在，不能证明语义推理正确；天气与忌口等判断仍需真实模型案例验收。
第四阶段已移除 modify 跳过审核的行为，并将网站修改接口接入同一审核入口，见下文。

## 第四阶段：修改后审核与版本失效

网站的 `/api/plan` 修改接口统一处理局部重新规划、全局修改、添加、删除和明确选择候选：

1. 保留用户请求的修改范围，更新完整活动、费用、餐厅候选和地图路线。
2. 清除旧的 audit/history/passed 等当前结论，revision 从旧版本加1；没有合法版本的老计划从1开始。
3. 将最终完整方案、实际来源快照和本次已更新的需求交给 ValidateAgent，返回新 audit/history。
4. 审核通过、警告、阻断或错误都对应新 revision。审核失败仍保留修改，顶层不将它伪装成修改失败。

返回保持原来的扁平结构（blocks/legs/plans 等），新增 revision、audit、passed、history 和 review_context。
客户端传回 profile/preferences/recent_trips 以保留同一语义审核上下文；未重复发送 basic 时可使用方案保存的 basic。
全局日期或预算变化后按新日期、新需求审核，不能沿用之前的硬预算。修改接口的历史只记录本次新版本审核。

修改接口先审核一次并保留显式修改；网站发现可修复严重问题后自动进入 `/api/plan/repair/stream`。
修复入口先重新核查实际快照，不信任客户端旧 audit，然后至多修复两次。
修复使用独立的 audit_repair 模式，不重复执行用户原始删除、替换指令，并保护手选餐厅、酒店和真实报价。
首次生成也至多自动修复两次，每个成功的新方案使用递增 revision。
独立 CLI 循环仍保留默认两轮及显式修改只审核一次的行为；网站通过 Orchestrator 处理新自动流程。

审核服务返回旧 plan_revision 时拒绝采用；服务不可用、结果格式无效或位置不属于新方案时返回 error。
前端只保存与当前 revision 相同的审核。请求处理中以 review_pending 隐藏之前的当前结论，
修改失败或取消且本地方案未改变时可继续使用原版本审核；成功修改后没有新审核就保持未审核。
被停止或被新请求替代的晚到响应不能覆盖当前方案；搜索快照也按实际已应用方案保存，避免混用另一份规划的候选。
历史聊天仍保留先前对话，不能把其中旧方案的建议当成当前审核。

revision 是本地草稿的顺序标记，不是数据库锁，也不证明不同浏览器里的草稿是同一份。
这一阶段准备审核状态数据并在修改回复中提示最新结果；第五阶段已接入详细问题定位、确认按钮规则与离线评估。

## 第五阶段：页面提示、定位与可复现评估

网站右上角审核浮窗显示当前版本的审核卡，区分正在处理、尚未审核、通过、有建议、需要修改和审核未完成。
只读取与当前 revision 一致的结果；处理期间不展示之前的结论。历史聊天保留原始记录，不代表当前版本。

问题列表按严重程度排序，显示类型、规则/模型来源、方案、日期、活动名、原因、建议及可展开的输入依据。
“定位活动”切换到实际对应方案，在行程中滚动并高亮关联活动，同时切换地图日期。
定位不会自动选中活动或发送修改；用户仍通过活动上的“选择修改”补充需求。
只有方案/日期的信息可以定位到该日期；整体问题和无法对应实际活动的信息不伪造定位。
来源匹配比例衡量给定搜索快照，不能表示真实世界准确率；缺失报价不能当作免费。

确认按钮和最终保存处理使用同一保护规则：

| 当前状态 | 能否确认 | 下一步 |
|---|---|---|
| passed | 可以 | 确认并保存历史行程 |
| warning | 可以 | 预订前核实提示 |
| blocked | 不可以 | 定位、修改问题并等待新审核 |
| error / 无审核 / 旧版本审核 | 不可以 | 重试审核，或重新生成没有有效版本的旧行程 |
| 正在处理 / 有选中的修改 | 不可以 | 完成或取消本次处理、修改选择 |

审核覆盖完整计划的全部备选方案，因此其他方案中的严重问题也会暂时阻止确认。
页面明确标出这一范围；不能凭前端过滤问题列表就声称单个方案已经通过。
页面示例数据没有真实审核与版本，不能直接确认保存；需要正式生成行程。
这些保护用于网站交互，不把客户端传入的 revision 或 audit 当成服务端签名/数据库锁。

### 单独重试审核

`POST /api/plan/review` 接收 `{plan, search}`，返回与修改接口一致的扁平结果。
只执行 ValidateAgent，不再次生成、替换、搜索或重算路线；活动、日期、需求和 revision 均保留。
使用方案的 basic、review_context（画像/偏好/历史）与完整来源重新检查。
请求中的不同日期、目的地、basic、修改指令和不合法版本会被拒绝；修改需求仍走 `/api/plan` 的修改流程。
结果错误仍保留原行程，审核结论是当前版本的 error，不能恢复旧通过结果。
前端取消重试或收到旧请求的晚到响应时，不能将它覆盖到新行程。

### 离线评估

固定案例在 `ValidateAgent/evaluation/cases.json`，由人工设计预期状态和严重问题定位。
包括预算格式、人数、备选方案、未知报价、旧费用汇总、时间重叠、真实路线耗时、缺失路线、
来源缺失、错误分店、来源别名、跨日列车、航班预留、空行程、选中餐厅索引0、模型合并与错误。
模型相关案例用 `hybrid_fixture` 标明预置输出；既不调用真实模型，也不评价真实模型能力。

在仓库根目录执行：

```bash
python3 -S ValidateAgent/evaluate.py
python3 -S ValidateAgent/evaluate.py --check
```

无需 venv、Key、SDK 或联网。第一条生成 `evaluation/report.json` 与 `report.md`；
第二条只核对保存报告，发现结果不符合人工标签、依据值不匹配或报告过期时退出码为1。
报告绑定案例集 SHA256，不记录随机时间，使用同一代码与案例可得到相同结果。
严重问题按类型、方案、活动ID集合及 rule/model 来源一对一计数；状态和提示类型也必须符合预期。
指标包括严重问题精确率/召回率、误阻断/漏阻断、依据值匹配率和给定来源覆盖率。
这些数值是小规模合成回归集的表现，不是生产准确率。完整问题、定位和依据保存在 JSON 报告中。

先生成正式行程，不使用前端示例作为完整审核验收。建议依次检查：

1. 填写目的地、日期、人数和明确预算，生成方案。审核版本必须与方案版本相同；通过/建议状态可确认。
2. 将预算调低到已知消费以下：检查新版本预算问题、原因和定位；需要修改时确认按钮禁用。
3. 修改活动时间造成重叠，或将有真实交通耗时的两个活动安排得过近：问题定位应高亮关联活动，调整后重新审核。
4. 添加、删除、替换景点，选择具体餐厅或酒店：用户明确选择应保留，新结论替换旧审核；地图、后续交通和费用同步更新。

   恢复配置并重启需要的服务，点击“重试审核”：版本和活动不变，审核结果更新。
7. 请求处理中点击停止，再发起新请求：晚到旧响应不得覆盖当前行程或恢复旧通过结论。
8. 登录后确认一份当前通过的行程，在历史行程核对保存的活动、版本和审核。

规则严重冲突会跳过模型，测试模型故障时应使用规则已经通过的方案。
自动测试验证状态与渲染逻辑、HTTP重试接口、修改后的版本和完整快照；实际浏览器点击、外部服务与真实模型语义仍需上述验收。

### 暂无报价的放行与模型回复错误

景点、活动、餐厅和酒店因 API 限制没有报价时，仅保留 medium 核实提示；
没有其他严重问题且模型审核完成时，状态为 warning，可以确认行程。
费用合计仍是已知小计，预算保持 unknown；不会把未知报价标为免费或声称总费用一定在预算内。
已知费用超过总预算仍由规则阻断。模型的专项预算 high 也必须引用已知金额超出明确上限的证据；
只引用未知报价或上限存在，不能证明超支。仅由价格缺失证据支持的模型完整性 high 降为建议。
有实际营业、天气、时间或明确忌口证据的冲突不会因同时存在未知报价而消失。

模型输出无效与未知报价是两个独立状态。无效 JSON、回复截断、引用了错误活动位置或协议冲突时，
审核器提供一次针对性重试；初次输出上限为4096 tokens，回复被截断时第二次增至8192 tokens。
两次仍失败会显示具体类别的错误，不能把尚未完成的模型审核直接标为通过。
确认按钮在真实模型错误时仍禁用；恢复服务后点击“重试审核”，现有活动和 revision 保留。
模型会被要求合并同类提示、只返回必要的叶子证据、最多6条优先严重的问题，减少冗长回复造成的截断。
这些改动验证了离线边界，截图中具体模型回复无效的原始原因需要以重试后的错误类别继续确认。


### 紧凑的模型回复与页面展示

模型只返回 passed、issues，不需要额外复述 feedback。detail/suggestion 限制为简短文字，
evidence 使用叶子路径列表，例如 `["plan.blocks[5].price_known", "search.weather.days[0].weather"]`，
不要求模型复制整个活动或字段 value。审核器从本次送入模型的输入读取值，转换为公共协议的
`[{"path": "...", "value": "实际输入值"}]`，再核对完整原始快照。具体对象或小集合路径会按下文规则展开为真实字段；不存在或过于宽泛的路径需要重新输出，
不能凭空补齐。旧版 path/value 回复仍会经过原有的真实性核对。
回复被截断时不能接受半段 JSON，也不能截掉严重问题后标记通过。

对话栏只报告审核完成、需要调整或尚未完成等简短状态；问题详情、建议、依据、定位和重试统一在右上角审核浮窗。
审核通过但有 medium/low 建议，不自动重新规划；反馈只包含有证据且 actionable=true 的 high 问题。
网页“重试审核”现接入流式审核与修复：先审核同一快照，如果通过或只有建议，活动和 revision 不变；
只有核实存在可修复严重问题才调用 Plan Agent。原 `/api/plan/review` 接口仍是只审核。


### 实时自动审核与修复窗口

默认右上角显示审核浮窗，地图仍在右下角；两个窗口都可以拖动、隐藏或展开。中间栏只展示行程。
审核窗口按服务端推送显示“生成方案 → 审核中 → 未通过原因与正在自动修复 → 新版本审核 → 最终结论”，
“查看处理过程”保留各轮版本与严重问题原因，当前问题定位始终使用当前版本的活动。
普通建议、暂无报价和模型服务故障不会触发反复重新规划，也不会在聊天中复制审核详情。

首次生成 `/api/plan/stream` 现在推送每次 plan/validate 完成后的完整快照、来源、audit、history、stage 和 repair_count。
修改后可修复阻断、网页重试审核以及“再次自动修复”使用 `POST /api/plan/repair/stream`：
先审核保存的最新行程和实际来源，再使用当前版本与 `high + actionable=true` 反馈修复。
最多修复两次，最终 workflow.stop_reason 区分 passed、limit、error、needs_information。
不保证模型必然修好；达到上限仍 blocked，保持确认禁用，可以再次尝试自动修复。
修复调用失败时保留上一次完整行程、版本和问题，显示 error，不能假装修复成功。

PlanAgent 的修复复用完整计划修改与最终重算：固定目的地、日期、人数和硬预算，
恢复未受影响的备选方案，保留用户明确选择及检索报价，重新计算餐饮锚点、费用和实际地图路线。
审核反馈中的金额是事实描述，不能按用户新报价格解析，避免为了“通过”而篡改报价。
自动修复使用精简的模型协议：只返回各方案、日期和活动的 id/name/type/time/note，
不要求模型复制路线折线、链接、候选餐厅、报价或审核数据；未换地点的元数据从原始记录恢复。
换地点不会继承旧经纬度或链接，报价仍由检索来源确定，用户明确选择仍由原有保护逻辑保留。
回复截断、JSON 格式无效、缺少原方案/日期或重复活动 ID 时，针对该回复自动重新生成一次。
这次格式重试不增加行程版本；两次仍失败则保留原行程，显示可读错误类别，不能接收半段 JSON。
格式重试与最多两轮行程修复是独立上限；离线故障测试不代表真实模型一定能解决行程冲突。
取消连接会停止 Orchestrator 与子进程，旧请求结果不会覆盖新请求或恢复旧通过结论。
只有最终当前版本通过且处理完成，才能确认保存；审核过程中可查看行程详情。

新增编排、规划与 HTTP 流式测试验证两次修复、实时未通过原因、修复失败保留原方案、上限和取消清理。
浏览器模拟以固定响应验证实际 React 页面、浮窗移动/隐藏/展开、修改后自动修复、取消晚到结果和移动端边界。
这些结果不等于真实模型保证通过；请重启后端并用真实搜索再次验收。

### 市内路线方式与间隔审核

Plan Agent 已有真实路线转场顺延逻辑：初次生成按路线耗时另留5分钟，修改时保留活动时间并提示。
原地图默认优先步行或公交；公交过慢不能证明同一间隔内驾车也无法到达。
现在对有完整同日活动时间且默认路线超出间隔的市内转场，额外核实驾车路线并采用较快的真实路线。
地图折线、mode、duration_s 与审核使用同一结果；需要改用驾车时在活动备注明确说明。
只缓存坐标对的默认路线和独立驾车路线，不把某次行程的方式选择污染其他行程。

规则按实际路线方式描述耗时与可用间隔，不再给景点或餐厅转场附加飞机/列车进出站要求。
航班120分钟、列车60分钟预留仍只适用于已选班次；打车去机场或地铁到火车站本身不等于乘坐航班/列车。
若仅有未固定的默认公交/步行路线偏慢，其他方式未核实，则只提示 medium，不据此阻断行程或自动重排。
有已核实可容纳的 alternatives 时不判为无法到达；mode_locked=true 的固定方式只能使用其本身耗时。
驾车也确实超出间隔、固定方式不足、真实时间重叠与赶不上班次，仍保留 high。
模型不能仅凭市内路线与活动时间重新引入已被排除的缓冲或方式假设；实际封路等语义证据仍可阻断。

已有方案点击“重试审核”会按新规则复核旧快照；缺少替代路线时只能提示核实，不会伪造驾车耗时。
重新生成或修改方案后，路线补全会实际核实较快方式。地图接口失败不做直线距离耗时估计来宣称已通过。
新增离线案例覆盖公交45分钟、驾车约14分钟与40分钟间隔，以及方式固定、驾车仍不足、进出站和模型误判。

### 模型依据路径的兼容与纠错

模型输入提示中的路径示例来自本次实际数据，避免将天气结构固定为 `search.weather.days`。支持路径外层空白、反引号、`$.` 前缀、单双引号字段，以及仅含 `path` 的记录。具体对象或小集合引用会展开为真实字段（最多 64 个，空集合保留为缺失信息的证据）；整个方案、活动列表等宽泛引用仍需改为具体字段。

不存在或范围过大的引用会触发一次完整重试，反馈包含错误路径、问题序号及当前输入中实际存在的附近字段。不会猜测字段、改变数组索引或丢弃严重问题来通过审核；连续错误仍保留原方案并报告审核未完成。旧版 `path/value` 记录继续核对值，不能用模型提供的值覆盖真实输入。
