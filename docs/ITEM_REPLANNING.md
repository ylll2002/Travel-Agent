# 活动替换与关联行程调整

## 交互约定

- 点击非天气活动块可选中，再次点击取消；支持同一方案中的多项选择。
- 有选中项目时，对话框占位符为「重新规划的原因...」，按钮为「重新规划」。
- 原因在原对话框输入，不弹窗；Enter 提交、Shift+Enter 换行。
- 选中项目或处理请求期间，「确认计划」不可点击。
- 成功后更新项目、后续时间、真实路线和已知费用，清空选择及输入，撤销旧确认状态。
- 提交重新规划后立即清空输入框，原因保留在聊天记录中；失败或取消时保留原方案和选中项目。取消仅停止客户端等待，已启动的后端任务可能继续运行。
- 同一餐饮时段只选一家餐厅；沿用主分支的餐厅切换接口立即更新计划、费用和地图，重新规划使用更新后的活动块。当前方案的未选餐饮推荐会先提示确定餐厅，以便计算真实交通路线；作为替换目标的餐饮推荐无需先选。
- 空响应、截断响应、无效JSON或缺少目标ID的模型结果纳入最多三次重试，并传入错误反馈；重试失败保留原方案。
- 新方案保留班次、出发站、到达站和去返方向。旧方案可按班次号、日期和时间匹配搜索结果，或读取明确的“机场/车站 → 机场/车站”备注；歧义班次不会自动选取。市内地铁、打车等按相邻地点的真实路线调整，不作为航班或火车截止时间。
- 点击天气不进入重规划。已有餐饮候选按钮仍可独立显示地图点，不会意外切换整个活动块的选择。

## 数据流

`AgentPage → POST /api/plan/replan → SearchAgent → PlanAgent/replan.py → 地图路线与约束检查 → 完整结果`

明确的替换操作绕过 QuestionAgent。现有自然语言整体修改接口保持原有行为。

客户端发送完整方案的 `blocks`，它们是本次修改的权威数据源。嵌套 `plans[].itinerary` 从块重新派生。
活动 ID 不重新编号；方案标识和日期共同界定操作范围。模型只能选择搜索候选 ID，不直接生成新地点、价格、坐标和时间。

请求示例：

```json
{
  "plan": {
    "destination": "杭州",
    "start_date": "2026-10-20",
    "end_date": "2026-10-22",
    "revision": 0,
    "blocks": [],
    "legs": []
  },
  "revision": 0,
  "plan_style": "推荐方案",
  "target_block_ids": ["b3"],
  "instruction": "换一个室内文化景点",
  "locked_block_ids": [],
  "profile": {},
  "basic": {"origin": "上海", "total_budget": "3000"}
}
```

示例中的 blocks 需替换为真实完整方案，包含选中 ID。

返回 `revision`、完整 `plan`、`changed_block_ids`、`affected_days` 和 `changes`。
校验失败返回 422，输入版本不一致返回 409，搜索/进程错误返回 502/503，超时返回 504。
目前没有服务端方案版本存储：revision 校验用于输入自洽，前端另用快照身份防止过期结果覆盖当前方案；不提供跨客户端并发控制。

## 调整规则

1. 优先复用搜索缓存；没有同类替代项时仅强制刷新搜索一次。
2. 在用户画像、原因和完整行程上下文中选择同类候选，排除原项目与重复景点。
3. 景点、美食与活动替换影响当天目标及后续时间；默认保留后续地点。
4. 酒店替换同步处理方案中同名住宿，并检查这些日期及次日酒店出发路线。
5. 同日航班/火车替换使用真实班次时间和机场/车站接续路线。缺机场信息或跨午夜班次会明确失败。
6. 高德返回实际路线耗时，普通接续额外预留 10 分钟，机场/车站另预留 60 分钟。
7. 次日默认最早 08:00 从酒店出发。更换酒店可推迟首项活动；没有修改目标前的安排保持原时间。
8. 显式 `locked_block_ids` 或 `fixed_time` 项目不被随意移动。超过当天 activity_window、23:30、营业时间冲突、无法赶上固定出行或已知费用超预算时，最多换候选重试三次，然后保留原方案。
9. 未配置高德、定位失败或缺少必须的路线时不会提交无法验证的方案。
10. 其他方案和不受影响日期的块与路线保留原值。

## 当前边界

- 营业时间/活动时间只在数据源提供明确时间时检查，不能保证网页未提供的信息。
- 默认保留原活动时长；本版不自动删除活动、换掉未选中的餐厅或把活动迁移到另一日期。当天容纳不下会尝试更近的候选，仍失败则提示用户调整范围。
- 价格沿用来源中的项目报价，属于估算。按人计费项目根据出行人数计算，酒店沿用 group 计费；房间数量及市内交通费用尚未统一计算。替换地点时清除旧报价来源、单价和计费基准。未知价格单独提示；有预算时不接受缺价格的替代项。
- 忌口、兴趣和文字原因由模型进行候选选择，时间、路线、候选身份和已知费用则通过确定性规则检查。
- 成功后需用户重新确认才通过原有行程记忆接口保存；登录用户的替换操作会记录移除和添加行为。
- 本次改动不解决原仓库其他接口的 Windows 路径问题，完整项目仍建议通过 WSL / Linux 运行。

## 验证

在仓库根目录运行无需外部服务的约束测试：

```bash
PlanAgent/.venv/bin/python -m unittest discover -s PlanAgent/tests -v
```

后端接口契约和原测试：

```bash
cd backend
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest
```

前端构建：

```bash
cd frontend
npm run build
```

验收：

- 使用前端模拟方案检查选择、取消选择、按钮状态、占位符、Enter 提交与天气不可选。
- 使用真实生成的方案和有效模型/高德配置，替换景点、美食、酒店，确认名称、时间、总价和地图同步更新。
- 其他方案保持不变；酒店变化后检查次日出发路线；航班变化后检查到达与接续时间。
- 餐饮推荐每个时段选择一家，确认重新规划请求使用所选餐厅；不同日期或时段可以选择同名餐厅。
- 检查航司名称不同但班次号一致、傍晚去程、旧方案机场备注和市内地铁/打车等情况；班次站点缺失提示应包含具体项目名称。
- 连续替换两次，确认目标 ID 稳定、revision 递增。
- 点击重新规划后确认输入框立即清空、聊天记录保留原因；模拟网络失败、取消、无候选、路线缺失、锁定冲突、超预算，确认旧方案未被覆盖。
- 成功后旧确认状态失效，可以重新确认并保存；未登录不影响本地重规划。
